# Source map and reporting contract

Inspected on 22 October 2026: `cognilune-websites` commit `1ef5f3e`, existing migrations through `069_workspace_plan_entitlements.sql`, billing verification routes, wallet functions, auth helpers, and the configured live PostgreSQL schema. The live schema contains additional actor, rollover, session, and workspace deletion fields. Optional fields are read through `to_jsonb(row)` so older compatible schemas do not require duplicate migrations.

## Filter semantics

Report boundaries are UTC `[start, end)`. A custom end date includes that calendar day; ongoing periods stop at the request's `asOf` timestamp. Maximum requested range is 732 days. Comparisons use the immediately preceding equally long interval, and show no percentage when the previous value is zero.

Current inventory, current wallets and entitlement status are labelled snapshots. Tables of users/workspaces/projects default to creation cohorts with an explicit **All creation dates** option. Current subscription and owner-balance tables always show the current inventory while credit columns use the selected period. Operation and payment tables always use the reporting period. Detail pages can open records created before the cohort; related histories retain the chosen reporting period.

Plan filters apply to current plans for inventory/usage and purchased plan for payment reports. A customer can own several plans, so per-plan unique-user counts must not be summed to produce the global customer count. Current Free/expired/inactive customers are not active paid subscribers. Purchasers count only confirmed payment records. Payment counts and amounts are not attributed to a project because no verified allocation exists.

Global search searches authorized customer/workspace/project records across creation dates. Table search, status, and activity controls affect that table; the globally positioned date, plan, owner, workspace, and project controls affect applicable report aggregates. Search text is escaped and all SQL values are parameters. Sort identifiers come from a fixed server allowlist.

Usage owner totals follow the charged workspace's current owner. The actual performer is separately retained as `actor_id` and displayed in the operation ledger. Member-created projects and member-performed operations are included when scoping a whole workspace, even if their creator differs from the workspace owner. Payments remain attributed to the recorded purchasing user.

## Deliberately unavailable

- True MRR and recurring renewals: fixed-term purchases are not automatic recurring collections.
- Refund amount, refund-date trend, and net revenue: status alone cannot distinguish partial versus full refunds or their dates.
- Lifetime credits allocated and a lifetime consumed/allocated percentage: daily refills and replacement grants have no complete allocation ledger.
- Per-operation ending balance: not persisted by the source.
- Complete subscription transition/cancellation history: paid-order history and current plan dates are available; absent historical events are not manufactured.
- Payment method/invoice linkage when missing: source fields are shown only when recorded; provider order ID is labelled as an order, not a fabricated invoice.
- Historical plan attribution: usage breakdowns are explicitly by the current plan. Purchased-plan attribution is available for payments.
- Deleted hard-record history: this dashboard cannot recover rows no longer retained upstream.
- Separate CRM website advertising subscriptions: the customer/workspace payment ledger does not provide a verified unified receipt ledger for those products. Customer plan revenue must not be presented as whole-company accounting revenue.

## Future upstream integrations

Implement an append-only allocation ledger and wallet transaction balance snapshots in the actual charging transaction to support allocation/percentage/history metrics. Add provider-signed refund events with refunded amount/currency/time and subscription lifecycle events for trustworthy net revenue, cancellation history, and recurring metrics. These are upstream accounting changes; adding empty duplicate tables in this dashboard would not make existing history accurate.
